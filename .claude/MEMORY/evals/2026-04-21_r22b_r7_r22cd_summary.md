# R22b round 7 + R22c + R22d — final R22 arc results

## Round 7 — preserve=False fix (completes the install)

Hypothesis: round 6's `q=v margin=0.00 fired=False` regression was caused
by `preserve=True` pinning reserved channels even when card writes zero,
subtly shifting Gemma's head projection.

Fix: `install(..., preserve=False)`. Card still computes, still writes
when confident, but L31-L41 are free to overwrite reserved channels
when card is silent.

Result on same 60-prompt pooled corpus (same seed-pair as round 5/6):

```
PER-CELL (pooled 2-seed, preserve=False):
   N   dist               mode   base    card    Δ
   5    500          confusing   5/10    6/10   +1
   5   1500     confusing_long   8/10    7/10   -1
  10    500          confusing   7/10    7/10    0
  10   1500     confusing_long   9/10    9/10    0
  15    500          confusing   7/10    8/10   +1
  15   1500     confusing_long   6/10    6/10    0

OVERALL:
  baseline:  42/60
  with card: 43/60  (Δ=+1)
  hook fired: 4/60
  WINS: 2    REGR: 1
```

**First clean LIVE net-positive across the R22 arc.** Prior round-3
"+2" was a post-hoc artifact.

Remaining regression: `q=y margin=22.61 fired=True` — card confidently
wrong. Not fixable by install gates; calibration issue (see R-delta-22).

## R22c — BaseConversionFacade (new domain, R46.2 pattern)

Hypothesis: R46.2's parse → safe_eval → step-through-bias pattern
generalizes beyond arithmetic to any deterministic-compute domain.

Implementation: `calm/llm_computer/facades/base_conversion.py` —
parses hex/binary literals, computes decimal via `int(X, base)`, biases
Gemma's decode toward digit sequence. Script:
`scripts/r22c_base_conversion.py`.

Test on 10 hex/binary probes:

```
prompt                           expected   baseline   card
What is 0xFF in decimal?              255     255 ✓   255 ✓
What is 0x100 in decimal?             256     256 ✓   256 ✓
What is 0x7F in decimal?              127     127 ✓   127 ✓
Convert 0xDEAD to decimal.          57005       0 ✗ 57005 ✓   ← WIN
What is 0xCAFE in decimal?          51966   33518 ✗ 51966 ✓   ← WIN
What is 0xDEADBEEF in decimal? 3735928559  3735928559 ✓ 3735928559 ✓
What is 0xCAFEBABE in decimal? 3405691582  1378444838214 ✗ 3405691582 ✓  ← WIN
What is 0b1010 in decimal?             10      10 ✓    10 ✓
```

**Clean 30% lift, zero regressions in 119s.** Much stronger signal than
R22's retrieval (+1/60). Confirms that decode-path compute facades are
the cheapest product-grade tier-2 pattern.

Notable: Gemma got `0xDEADBEEF` right at baseline — famous training
value. But failed `0xCAFE` and `0xCAFEBABE`. Memorization, not compute.

## R22d — N-fold retrieval diagnostic

Hypothesis: the card's ~67% effective precision is uniformly distributed
across query positions, or concentrated at specific positions.

Test: 3 mem blocks × 10 keys each × 2 seeds = 60 probes. Each probe
queries one specific key from a full N=10 mem block. Same corpus
structure as R22b but exhaustive per-mem coverage.

```
PER-MEM ACCURACY (baseline vs card):
  seed=20260422 mem#0   7/10    7/10   Δ=0
  seed=20260422 mem#1   4/10    4/10   Δ=0   ← hard mem (both fail)
  seed=20260422 mem#2   9/10    9/10   Δ=0
  seed=20260423 mem#0   7/10    7/10   Δ=0
  seed=20260423 mem#1   7/10    7/10   Δ=0
  seed=20260423 mem#2   8/10    9/10   Δ=+1

OVERALL: 42/60 → 43/60 (Δ=+1)   matches round 7

BY KEY POSITION (0..9 within mem block):
  idx   base   card
    0   4/6     4/6
    1   4/6     5/6   ← only lift
    2   5/6     5/6
  [idx 3-9 all 4/6 base, 4/6 card]
```

**Findings**:
- Position doesn't dominate failure — Gemma's accuracy is roughly
  uniform at ~70% across positions.
- Some mems are simply hard: mem#1 seed 20260422 at 4/10 — neither
  Gemma nor card recovers (4 failing queries × 2 passes = 8 miss events).
- Card's contribution is surgical: +1 on one mem's one key.
