# R16 — PT+Delta scratchpad null (2026-04-21)

Single-round scratchpad test. Both plain PT and PT+Delta fail at
0% full-expression match. Informative null: state-carry alone
doesn't substitute for arithmetic lookup — PT+Delta has a
mechanism for carrying values across decode steps but no
mechanism for computing them.

## Task format

Generated by `gen_scratchpad_batch(depth, count, seed)`. Input is
a nested expression; target is step-by-step evaluation.

  depth=3:
    Q:    ( ( ( 3 - 2 ) - 5 ) - 2 )
    expr: 3 - 2 = 1 ; 1 - 5 = -4 ; -4 - 2 = -6

  depth=5:
    Q:    ( ( ( ( ( 1 - 2 ) * 2 ) + 6 ) * 3 ) + 5 )
    expr: 1 - 2 = -1 ; -1 * 2 = -2 ; -2 + 6 = 4 ; 4 * 3 = 12 ; 12 + 5 = 17

Three computations woven together:
1. Parse nested expression (left-associative, parenthesized)
2. Perform arithmetic: single-digit operands, 1-3 digit intermediates,
   ops `+`, `-`, `*`
3. Emit step-by-step trace referencing running value from prior step

Eval metric: **full-expression exact match** — every token correct
across the whole trace. Very strict; one digit wrong → example fails.

## Results (2000/N × 30ep, N=[3,5], max_len=128)

| | ep30 final | loss | Status |
|---|---:|---:|---|
| Plain PT | **0% / 0%** | 0.23 | Token-level learning happens (loss down 85%), no exact traces |
| PT+Delta (ep12, killed early) | **0% / 0%** | 0.29 | Same trajectory as plain PT |

Killed R16 at PT+Delta ep12 — loss trajectory mirrors plain PT
exactly (1.4 → 0.4 over 9 epochs both), no sign of mechanism
advantage emerging. Remaining 18 epochs wouldn't crack 0%.

## Why both fail

The task requires three capabilities simultaneously at 185K params:

1. **Structural parsing of nested expression** — fits at this scale
   (PT variants solved similar structure tasks in session 31)
2. **Arithmetic lookup table** — requires 9×9×3 = 243 entries for
   single-digit ops PLUS multi-digit carries. Too many facts for
   185K params to memorize reliably.
3. **State-carry for intermediate values** — PT+Delta has this via
   Householder rule; plain PT has to re-derive from prior emitted
   tokens.

The arithmetic lookup (2) is the bottleneck. PT+Delta's state-carry
advantage is irrelevant if the model can't compute the values to
store.

**The delta rule doesn't "do arithmetic."** It stores and retrieves
(k, v) associations via `S_new = S - β(S@k - v)⊗k`. Computing 3*7=21
from the tokens `3`, `*`, `7` is an FFN / attention learning problem,
not a delta problem. At 185K params, the FFN can't internalize the
full arithmetic table alongside grammar.

## Reinforcing the Brain+Cards thesis

R16 is evidence FOR the substrate's core composition claim: **different
capabilities need different mechanisms**:

- **Compute** (3*7=21, 17+23=40) → compiled cards (`adder`, `multiplier`,
  gate-graph IR). Exact by construction.
- **Associative recall** (find value of k in prefix) → PT+Delta
  (R13/R15 data).
- **Structure extraction** (parse NL → expression) → PT
  (CopyAugmentedTransformer, session 31).
- **Natural language understanding + routing** → Gemma.

No single 185K-param card does all of these. Trying to force one
mechanism to span all (like R16's scratchpad) produces a null.

**Correct deployment:** scratchpad-like tasks should be
decomposed:
1. Gemma parses the nested expression → emits tokens
2. PT extracts arithmetic operations as structured triples
3. Compiled `safe_eval` card computes each step
4. VerificationHook injects each result as Gemma's next token
5. PT+Delta tracks running value for downstream steps that
   depend on it

The scratchpad eval as currently structured measures a single
card's joint capability. That's not what the substrate is
supposed to do.

## Possible R17 (deferred): pure state-carry, no arithmetic

A cleaner test of PT+Delta's state carry would remove the
arithmetic requirement:

  Q: x = 5 ; y = 7 ; emit x y x y
  expr: 5 7 5 7

No computation, just echo a stored value. Expect PT+Delta wins
here cleanly while plain PT struggles (softmax would need to
attend repeatedly to the same input position, which works up to
a limit).

Not run — R16's null is enough to establish the "arithmetic
requires compiled cards" point, and the R13+R15 data already
covers the state-carry-for-retrieval case.

## Key signal

**Plain PT and PT+Delta have nearly identical loss trajectories**:

  epoch | PT loss | PT+Δ loss
  ------|--------:|----------:
  1     | 1.42    | 1.41
  3     | 0.60    | 0.54
  6     | 0.47    | 0.40
  9     | 0.40    | 0.33
  12    | 0.36    | 0.29

If PT+Delta's state carry was helping, PT+Delta's loss would
diverge below plain PT's at some epoch. It doesn't. Both are
bottlenecked on the same capability (arithmetic), so their
learning curves track.
